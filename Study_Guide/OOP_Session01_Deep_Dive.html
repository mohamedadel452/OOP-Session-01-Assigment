شرايح 3 – 4

1) الـ OOP: ما بعد التعريف

تشبيهماكينة الـ ATM. بتديك أزرار (methods) تعمل بيها حاجات محددة، وعمرك ما بتفتح الماكينة وتمد إيدك على الفلوس (state). الماكينة هي الوحيدة المسموح لها تغيّر رصيدها، وبقواعدها هي. ده جوهر الـ OOP: ربط الـ state بالكود الوحيد المسموح له يغيّره.

ليه الـ OOP اتخلق أصلًا؟

المشكلة الحقيقية

في البرمجة الإجرائية (procedural) الداتا بتبقى متاحة لأي function. لما البرنامج يكبر، أي function ممكن تبوّظ داتا function تانية، ومحدش يعرف مين غيّر إيه ومتى. الـ OOP مش "طريقة نحاكي بيها العالم الحقيقي"، هو أداة للتحكم في مين يقدر يغيّر الـ state. الـ class هو الحدود اللي بترسمها حوالين الـ state والكود المسؤول عنه.

مفهوم غلط (الشريحة بتلمّح له)الحقيقة
"الـ OOP بيحاكي العالم الحقيقي"ده استعارة تعليمية مفيدة للمبتدئ، لكنها بتضلّل في التصميم. الـ objects في الأنظمة الحقيقية بتمثّل مسؤوليات مش أشياء: PaymentProcessor وOrderValidator مالهمش وجود في العالم الحقيقي. وفي الشريحة 4، Student.Study() وStudent.TakeExam() أفعال واقعية، لكن نظام تسجيل طلبة حقيقي عمره ما هيكتب Study(). اللي بيهمه: Enroll وRecordGrade.
"OOP = classes"الـ class مجرد آلية. لو كل الـ fields عامة وكل الـ methods بتاخد الـ object وتعدّل فيه من بره، تبقى كتبت كود إجرائي جوه classes.
"الـ OOP يعني reusability"إعادة الاستخدام عن طريق الـ inheritance غالبًا بتعمل coupling سيئ. الأفضل في الغالب composition (هنوصلها في السيشنز الجاية).
"كل حاجة في C# هي object"صح على مستوى الـ type system (حتى int بيرث من System.Object)، لكن مش معناها إن كل حاجة instance على الـ heap. int نفسه struct (System.Int32) وبيتخزن inline. هنشوف ده في القسم 2.

الـ object في الميموري: ليه ده يهمك؟

الـ instance لأي class على x64 ليه overhead ثابت قبل ما تحط field واحد:

الجزءالحجموظيفته
Object header8 bytesبيتستخدم للـ lock وللـ hash code وبعض حالات الـ GC
Method Table pointer8 bytesبيحدد نوع الـ object وبيدعم الـ virtual calls والـ type checks
الـ fieldsحسب النوعالـ state بتاعك

يعني class Point { int X, Y; } حجمه حوالي 24 bytes (16 overhead + 8 داتا) لأن أقل حجم لـ object هو 24 bytes، غير الـ reference نفسه (8 bytes) اللي بيشاور عليه. الرقم ده هو السبب الحقيقي اللي عملنا عشانه الـ struct (القسم 2).

الـ Aliasing: أول باج بيقابلك بين الـ class والـ struct

var a = new Student { Name = "Ali" };
var b = a;                       // بينسخ الـ reference مش الـ object
b.Name = "Sara";
Console.WriteLine(a.Name);       // "Sara" ← a وb بيشاوروا على object واحد
في الإنتاجده أصل باجات زي: تعدّل object جوه method فتتغيّر حاجة في مكان بعيد خالص، أو cache بيرجّع نفس الـ object لطلبين فيحصل تداخل بين مستخدمين. مقارنته بالـ struct (نسخة مستقلة) هي اللي هتخلّيك تفهم القسم الجاي.

"Objects Communicate" (الشريحة 4)

الميكانيزم

الـ method call على instance عادي في .NET هو فعليًا call لـ function عادية، والـ object بيتبعت لها كـ argument مخفي اسمه this. لما تتعامل مع virtual methods بيدخل الـ Method Table pointer في اللعبة عشان يحدد أنهي implementation يتنادى. (ده موضوع Polymorphism في سيشن جاي.) فكرة "الرسائل" جاية من Alan Kay: الـ object بيستقبل رسالة ويقرر بنفسه يعمل إيه.

ملاحظة سينيور

اسأل نفسك عن أي class: "مين المسموح له يغيّر الحالة دي؟" لو الإجابة "أي حد"، مفيش encapsulation حتى لو كل الـ fields عندك private وكل حاجة عاملها property بـ get; set;. وكمان مبدأ Tell, Don't Ask: بدل ما تسأل الـ object عن حالته وتقرر أنت من بره، قوله يعمل الشغل (order.Ship() بدل if (order.Status == Paid) order.Status = Shipped).

2) Struct

تشبيهالـ struct زي ورقة فيها رقم تليفون بتصوّرها وتدّيها لصاحبك: هو بيكتب عليها ويشخبط براحته، وورقتك ما بتتأثرش. الـ class زي لينك Google Doc: كل اللي معاهم اللينك بيعدّلوا في نفس المستند.

2.1) الشريحة بتقول إيه، وإيه اللي محتاج تصحيح؟

اللي في الشريحة 5التصحيح الدقيق

2.4) new على struct مبتحجزش heap

Point p = new Point();   // مفيش heap ومفيش constructor call: المترجم بيطلع initobj (تصفير الـ bytes)

Point q;                 // ✅ مقبولة: مش لازم new لو هتعيّن كل الـ fields بنفسك
q.X = 1; q.Y = 2;
q.Print();
مفهوم غلط"new يعني heap". ده صح للـ classes بس. للـ struct، new معناها "استدعي الـ constructor على المكان اللي المتغير فيه". وكمان ده هو سبب إن الـ compiler يقبل Point q; من غير new طالما عيّنت كل الـ fields (Definite Assignment).

2.5) Copy by Value: التفاصيل اللي الشريحة 10 مبتقولهاش

النسخ بيحصل في: الـ assignment، وتمرير الـ argument، والـ return، والـ foreach variable، وعند الـ boxing/unboxing، وعند قراءة property أو indexer بيرجّع struct. كل مرة الـ compiler بيعمل نسخة كاملة من الـ bytes.

مفهوم غلط: "النسخة مستقلة تمامًا"

النسخة shallow: بتنسخ الـ bytes، ولو فيها reference field بتنسخ الـ reference مش الـ object اللي بيشاور عليه.

struct Holder { public int[] Data; public int Count; }

var a = new Holder { Data = new[] { 1, 2, 3 }, Count = 3 };
var b = a;               // نسخة
b.Count = 99;            // a.Count لسه 3 ✅ (مستقلة)
b.Data[0] = 100;         // a.Data[0] بقت 100 ❌ (نفس الـ array)
Trade-off: struct كبير = نسخ كتير

لو الـ struct حجمه 64 bytes، كل تمرير بالقيمة بينسخ 64 bytes. الحل المعتاد in parameter (تمرير by readonly reference)، لكن لو الـ struct مش readonly الـ compiler ممكن يعمل defensive copy جوه الـ method فتضيع الفايدة. الحل: readonly struct (في 2.9).

2.6) ليه الـ struct مبيقدرش يرث؟ (مش قيد تعسفي)

السبب التصميمي

الـ instance من struct مفيهوش object header ولا Method Table pointer، وحجمه ثابت ومحدد وقت الـ compile، ومتخزن inline. الـ inheritance محتاج (1) virtual dispatch عن طريق الـ Method Table، و(2) إن متغير من نوع الأب يقدر يشيل ابن أكبر حجمًا. الاتنين مستحيلين مع تخزين inline بحجم ثابت. لو سمحوا بيها كنت هتقع في object slicing زي C++: تعمل Base b = derived فيتقطع الجزء الزيادة. عشان كده اللي بيتاح ليك: interfaces (وبيحصل boxing لو استخدمتها كـ interface).

2.7) فخاخ الـ Mutable Struct: أخطر جزء في القسم

لأن كل قراءة بتنسخ، أي كود بيعدّل على النسخة بيبان شغال وهو مش بيعمل حاجة. الـ compiler بيحميك في بعض الحالات ويسكت في غيرها.

struct Point { public int X, Y; public Point(int x, int y) { X = x; Y = y; } }

var list = new List<Point> { new Point(1, 2) };
// list[0].X = 10;            // ❌ CS1612: القيمة الراجعة نسخة مؤقتة مش variable
var p = list[0]; p.X = 10;    // بتعدّل نسخة، والـ list لسه (1, 2)
list[0] = p;                  // ✅ لازم تكتب النسخة تاني

var arr = new[] { new Point(1, 2) };
arr[0].X = 10;                // ✅ شغال: عنصر الـ array هو variable مش قيمة راجعة
foreach (var q in list) { /* q.X = 0; */ }   // ❌ CS1654: q متغير قراءة فقط

class Shape { public Point Origin { get; set; } }
var s = new Shape();
// s.Origin.X = 5;            // ❌ CS1612: الـ getter بيرجّع نسخة

struct Counter { public int N; public void Inc() => N++; }
class Holder { public readonly Counter C = new Counter(); }
var h = new Holder();
h.C.Inc();                    // بتتنفذ بدون error!
Console.WriteLine(h.C.N);     // 0 ← الـ Inc اشتغلت على نسخة دفاعية (defensive copy)
في الإنتاجالحالة الرابعة أخطرهم: مفيش error ولا warning، والكود بيبان صح، والنتيجة غلط. بتتكرر بالذات مع struct فيها methods بتغيّر الحالة (زي counters وaccumulators وstate machines) متخزنة في readonly field.
الحلخلّي الـ struct immutable: readonly struct وكل الـ members للقراءة فقط، وعدّل بإنك تعمل instance جديد (p = p with { X = 10 } مع record struct، أو ctor جديد). وكده الـ compiler نفسه بيمنع الفخاخ دي.

2.8) Boxing وEquality

  • Boxing: object o = p; أو تحويل struct لـ interface بينسخه على الـ heap (allocation + GC). لو حصل جوه loop ساخن تحس بالفرق.
  • الـ default equality: ValueType.Equals لو الـ struct فيه reference fields أو padding بيقارن بالـ reflection (بطيء وبيعمل allocations)، والـ GetHashCode الافتراضي مش مصمم يكون hash قوي (ممكن يعتمد على field واحد بس).
  • مفتاح في Dictionary: struct ما بيطبّقش IEquatable<T> بيخلي المقارنة تعدّي على Equals(object) فيحصل boxing في كل مقارنة.

استخدم struct فقط لو النوع: (1) بيمثّل قيمة واحدة منطقيًا زي الـ primitives، (2) حجمه أقل من حوالي 16 bytes، (3) immutable، (4) مش هيتعمله boxing كتير. لو واحدة منهم مش متحققة، استخدم class. وأمثلة الشريحة (إحداثيات، ألوان، فلوس) منطقية بشرط الـ immutability. وفي .NET نفسه: int، double، decimal، DateTime، Guid، TimeSpan، Nullable<T> كلها structs.

3) Constructors & Overloading

تشبيهالـ constructor هو فحص الجودة في آخر خط الإنتاج: مفيش منتج يوصل للعميل إلا لو عدّى الفحص. لو الفحص ضعيف، كل المنتجات اللي بتخرج ممكن تبقى معيبة، ومحدش هيكتشف غير لما العميل يستخدمها.

3.1) إيه اللي بيحصل فعلًا عند new Student("Ali", 20)؟

الميكانيزم (للـ class)
  1. الـ runtime بيحجز ميموري على الـ heap للـ object (header + Method Table pointer + fields) وبيصفّرها كلها.
  2. بيشغّل الـ field initializers (لو موجودة).
  3. بينادي الـ constructor (اسمه في الـ IL هو .ctor).
  4. بيرجّع الـ reference.

الـ object مستحيل يوصل لكودك قبل ما الـ constructor يخلّص، إلا لو أنت سرّبت this جواه (مثلًا اشتركت بيه في event أو حطيته في static list).

3.2) القواعد الأربعة في الشريحة 7: ليه؟ وإيه اللي ناقص؟

القاعدةالسبب الحقيقياللي ناقص
1) الاسم = اسم الـ classده اللي بيميّزه عن باقي الـ methods لغويًاالـ IL بيسمّيه .ctor دايمًا، والاسم في الـ C# مجرد syntax
2) مفيش return type (ولا void)ناتج new هو الـ object نفسه، فمفيش قيمة تانية ترجع. لو كتبت public void Car() جوه class Car فده مش constructor، ده خطأ CS0542 (member ما ينفعش يكون اسمه زي الـ class)الـ compiler بيرفض الاسم أصلًا، مش بيعتبرها method عادية
3) بيتنادى تلقائيًا بـ newالـ new هي اللي بتحجز وتصفّر وتشغّلمش دايمًا: Activator.CreateInstance والـ reflection بينادوه، لكن MemberwiseClone وبعض الـ serializers بيبنوا الـ object من غير ما ينادوه

public class Student
{
    public string Name;

var s = new Student();   // ❌ CS7036: مفيش argument للـ parameter المطلوب

  • الـ default constructor اللي المترجم بيولّده public للـ class العادي، وprotected للـ abstract class، ومفيش واحد للـ static class.
  • Static constructor (static Student() { }): بيتنفذ مرة واحدة قبل أول استخدام للـ type. لو رمى exception، النوع كله بيتعلّم "فاشل" ويرمي TypeInitializationException في كل استخدام بعد كده طول عمر الـ process. باج بيقلب كل الـ requests بعد أول فشل.

3.5) Constructor Overloading (الشريحة 9)

الميكانيزم: Overload Resolution بيحصل وقت الـ compile

الـ compiler بيختار الـ overload حسب الـ type المعلن للـ argument، مش الـ type الفعلي وقت التشغيل. لو أكتر من واحد مناسب، بيختار "أحسن conversion". ولو مفيش أحسن واضح يطلع CS0121 (ambiguous).

void Print(int x)    => Console.WriteLine("int");
void Print(long x)   => Console.WriteLine("long");
void Print(object x) => Console.WriteLine("object");

Print(5);              // int    (تطابق تام)
Print((short)5);       // int    (short → int أفضل من short → long)
object o = "hello";
Print(o);              // object (النوع المعلن، مش الفعلي)

تصحيح

4) Encapsulation

تشبيهعداد الكهربا. بتقرا رقمه (get)، لكن مش بتقدر تفتحه وتعدّل الرقم بإيدك. شركة الكهربا بس هي اللي تقدر تغيّره، وبإجراءات محددة. لو كان أي حد يقدر يكتب الرقم، الفواتير كلها تفقد معناها.

4.1) مفاهيم غلط شائعة (وأول واحد في تعريف الشريحة)

مفهوم غلطالحقيقة
"Encapsulation = نخلي الـ fields private"الـ private وسيلة مش هدف. الهدف هو حماية الـ invariants: القواعد اللي لازم تفضل صحيحة طول عمر الـ object (رصيد مش سالب، طلب مش بيتشحن من غير دفع). لو عملت كل field private وضفت لكل واحد get; set; عامة، رجعت لنفس المشكلة بأسماء تانية (وده اسمه Anemic Model).
"Encapsulation = Data Hiding"الإخفاء جزء منها. الفكرة الأكبر إن الـ class يضمن بنفسه إنه دايمًا في حالة صالحة.
"الـ private بيحمي البيانات"ده حماية للمبرمجين من بعض وقت الـ compile، مش حماية أمنية. الـ reflection بيقدر يقرا ويكتب أي private field لو الـ code مسموح له. متعتمدش عليه لحماية أسرار.
اختبار عملي

اسأل: "هل ممكن كود خارجي يحط الـ object ده في حالة غير صالحة؟" لو الإجابة أيوه، الـ encapsulation ناقص مهما كانت الـ modifiers.

4.4) تسريب الـ Internals (Leaky Encapsulation)

الشريحة 11 بتقول "التغيير جوه الـ class ما بيأثرش على اللي بره". ده صحيح بس لو الـ class ما سرّبش تفاصيله:

public class Order
{
    private readonly List<OrderLine> _lines = new();
    public List<OrderLine> Lines => _lines;      // ❌ order.Lines.Clear() من أي مكان
    public IReadOnlyList<OrderLine> Lines2 => _lines;   // ⚠ ((List<OrderLine>)o.Lines2).Clear() لسه شغالة
}
public class Order
{
    private readonly List<OrderLine> _lines = new();
    private readonly ReadOnlyCollection<OrderLine> _view;   // اتعمل مرة واحدة
    public Order() { _view = _lines.AsReadOnly(); }

المثال كويس كبداية: الـ field private، والـ methods بتتحقق، والـ exceptions مناسبة. لكن فيه 4 نقاط لازم تعرفها:

public sealed class InsufficientFundsException : InvalidOperationException
{
    public InsufficientFundsException(decimal balance, decimal requested)
        : base($"Insufficient balance: {balance}, requested {requested}") { }
}

public sealed class BankAccount
{
    private readonly object _gate = new();
    private decimal _balance;

    public decimal Balance { get { lock (_gate) return _balance; } }

    public void Deposit(decimal amount)
    {
        EnsurePositive(amount);
        lock (_gate) _balance += amount;
    }

    public void Withdraw(decimal amount)
    {
        EnsurePositive(amount);
        lock (_gate)
        {
            if (amount > _balance) throw new InsufficientFundsException(_balance, amount);
            _balance -= amount;
        }
    }

    private static void EnsurePositive(decimal amount)
    {
        if (amount <= 0) throw new ArgumentOutOfRangeException(nameof(amount), "Amount must be positive");
    }
}
var acc = new BankAccount();
Parallel.For(0, 100_000, _ => acc.Deposit(1));
Console.WriteLine(acc.Balance);   // المتوقع 100000؛ بدون lock ممكن يطلع أقل (race)
Trade-off

الـ lock بيحمي instance واحد جوه process واحد. في نظام حقيقي الحساب بيتحمّل من الـ database في كل request، فطلبين على سيرفرين مختلفين مش هيتحمواش بالـ lock. الحماية هناك بتيجي من الـ database: optimistic concurrency (عمود RowVersion) أو transaction بـ isolation مناسب. والـ encapsulation بيحمي الحالة جوه الميموري، والـ database بيحميها بين الـ requests.

ملاحظة سينيور
  • خلّي الـ classes sealed افتراضيًا إلا لو صممتها للوراثة: الوراثة بتفتح باب لكسر الـ invariants من الابن.
  • لو محتاج اختبار كود internal استخدم [assembly: InternalsVisibleTo("MyApp.Tests")] بدل ما تخليه public.
  • Law of Demeter: a.B.C.DoSomething() معناها إنك عارف تفاصيل ما جوه a وB. الـ encapsulation الحقيقي إنك تقول a.DoSomething().

5) Properties

تشبيهموظف الاستقبال في مبنى. مش بتدخل المخزن بنفسك، بتطلب من الموظف: هو بيتحقق منك، وبيجيب لك اللي مسموح لك بيه، وبيسجّل لو في حاجة اتغيّرت. ومن بره بيبان كأنك بتتعامل مع المخزن مباشرة.

  • EF Core بشكل افتراضي غالبًا بيكتب في الـ backing field مباشرة وقت تحميل الـ entity، فالـ setter validation مش بيتنفذ على الداتا اللي جاية من الـ database. ده كويس (متكسرش التحميل) لكنه معناه إن داتا غلط في الـ DB مش هتتكتشف من الـ setter.

6) Indexers

تشبيهفهرس الكتاب: بتقول "الصفحة 42" أو "كلمة X" وبيجيبلك اللي عايزه، من غير ما تعرف الكتاب مترتب ازاي من جوه. الـ indexer هو الفهرس اللي بتحطه على الـ class بتاعك.

6.1) الـ Indexer تحت الغطا: property اسمها Item

الميكانيزم

الـ indexer مش syntax خاص في الـ CLR. هو property عادية معاها parameters. المترجم بيولّدلها get_Item(index) وset_Item(index, value)، وبيحط على الـ class attribute اسمه [DefaultMember("Item")] عشان اللغات التانية تعرف إن للـ class ده default indexed property.

ليه اسمها Item؟ وليه ممكن تتغير؟

الـ CLR نفسه ما فيهوش مفهوم []: اللي فيه هو properties بتاخد parameters، وكل لغة بتعرضها بطريقتها (C# بـ []). عشان كده لازم يبقى ليها اسم في الـ metadata. وتقدر تغيّره بـ [IndexerName("Number")] (الـ string نفسها indexer بتاعها اسمه Chars).

في الإنتاجلو عرّفت indexer وعرّفت كمان member اسمه Item في نفس الـ class تطلع CS0102 (تعريف مكرر)، لأن الاتنين بيتحوّلوا لنفس الاسم في الـ metadata.

أسئلة مقابلات (مع الإجابات)

جاوب الأول في دماغك، وبعدين افتح الإجابة.

1) هل الـ struct بيتخزن على الـ stack دايمًا؟

لأ. بيتخزن في المكان اللي معرَّف فيه: local عادي (stack أو register)، أو جوه الـ heap لو كان field في class أو عنصر في array أو captured في closure أو boxed. النوع الوحيد المضمون stack-only هو ref struct.

2) ليه list[0].X = 5 بتفشل لو list من struct، لكن arr[0].X = 5 بتنجح؟

indexer الـ List<T> بيرجّع نسخة (getter عادي)، فالتعديل على قيمة مؤقتة والـ compiler بيمنعه (CS1612). عنصر الـ array هو variable حقيقي، فبتعدله مباشرة.

3) إيه اللي بيحصل لو كتبت constructor بـ parameters في class؟

الـ default parameterless constructor بيختفي. أي كود بينشئ الـ object بدون arguments (new T() constraint، أو serializers، أو Activator) هيفشل، وأحيانًا وقت التشغيل مش وقت الـ compile.

4) إيه ترتيب التهيئة لما class B يرث من A؟

field initializers في B، بعدين field initializers في A، بعدين constructor بتاع A، وأخيرًا constructor بتاع B.

5) ليه ما ننادّيش virtual method من constructor؟

لأنها هتنفذ override الابن قبل ما constructor الابن ينفذ، فالابن لسه في حالة غير مكتملة (fields اللي بتتعيّن في الـ constructor لسه null أو default).

6) الفرق بين { get; } و{ get; init; } و{ get; private set; }؟

الأولى تتعيّن في constructor بس. التانية تتعيّن في constructor أو object initializer وبعدها تتقفل. التالتة تتعدّل في أي وقت من جوه الـ class (فأي method تقدر تتخطى القواعد). الأولى والتانية للـ immutability، والتالتة للـ entities ليها state بتتغير.

7) هل الـ auto-property { get; set; } يعتبر encapsulation؟

مش بحد ذاته. هي بتسمح بأي قيمة زي الـ public field. قيمتها إنها "ضمان مستقبلي": تقدر تضيف logic بعدين من غير ما تكسر الـ binary compatibility، وبتشتغل مع serializers والـ interfaces.

8) متى تعمل property ومتى method؟

property لو القراءة سريعة ومن غير side effects ونفس النتيجة لنفس الحالة. غير كده method (لو غالية أو فيها I/O أو بتغيّر حاجة أو محتاجة parameters).

9) ليه الـ optional parameters خطر في مكتبة عامة؟

القيمة الافتراضية بتتكتب جوه الـ IL بتاع المستدعي وقت الـ compile. لو غيّرت الـ default في نسخة جديدة، الـ assemblies القديمة لسه بتبعت القيمة القديمة لحد ما تتعمل recompile. الأمان: استخدم overloads.

10) إيه الفرق بين const وstatic readonly وreadonly field؟

const قيمة ثابتة وقت الـ compile وبتتحرق في كود المستدعي (نفس فخ optional parameters). readonly بيتعيّن وقت التشغيل في constructor أو initializer، وكل instance ممكن ياخد قيمة مختلفة. static readonly بيتعيّن مرة واحدة للـ type كله وقت التشغيل. لو القيمة ممكن تتغير بين إصدارات المكتبة، استخدم static readonly.

11) ليه ما ينفعش يبقى فيه indexer static؟

لأنه معرَّف بـ this[...] فهو مربوط بـ instance بالتعريف. الـ static مالوش this.

12) إيه هو الـ defensive copy؟ ومتى بيحصل؟

لما تنادي method على struct متخزن في readonly field (أو تمرره بـ in) وهو مش readonly struct، الـ compiler بيعمل نسخة مؤقتة عشان يضمن إن الـ method ما تعدّلش الأصل. نتيجته: الـ method بتشتغل على النسخة فالحالة الأصلية ما بتتغيرش، وتكلفة نسخ إضافية. الحل: readonly struct.

Constructor Checklist

  1. الـ object بعد الـ constructor في حالة صالحة دايمًا؟ (مفيش null أو default غير مقصود)
  2. المنطق في constructor واحد (master) والباقي بـ : this(...)؟
  3. مفيش virtual call ولا I/O ولا تسريب لـ this جواه؟
  4. لو كتبت constructor بـ parameters: هل حد محتاج parameterless (serializer, generics)؟
  5. لو struct: هل فيه مسار بيعمل default أو array من غير ما ينادي الـ constructor؟

Encapsulation Checklist (للـ Code Review)

  1. هل كود خارجي يقدر يحط الـ object في حالة غير صالحة؟
  2. هل بنرجّع collection أو object داخلي مباشرة؟ (استخدم IReadOnly... أو wrapper)
  3. هل set عام محتاجه فعلًا؟ ولا init أو private set أنسب؟
  4. هل القواعد في الـ class نفسه ولا في الـ controller؟
  5. هل الـ class thread-safe لو هيتشارك بين threads؟
  6. هل الـ struct بتاعي immutable؟
  7. هل بستخدم required و nullable annotations بدل null!؟
